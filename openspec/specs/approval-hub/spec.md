## Requirements
### Requirement: Level 1 — 許可要求の通知のみ (Attention 表示)
CLI が確認要求 (Notification 系イベント) を発火したとき、amm は該当ペインに `HasAttention` フラグを立て、タイトルバー/ボタンのオレンジ表示とタイトル絵文字 (⚠) で人間に知らせなければならない (SHALL)。回答自体はペイン内で行い、amm は代答しない。

#### Scenario: 非フォアグラウンド時の通知
- **WHEN** amm がフォアグラウンドでない状態でペインが attention 状態になる
- **THEN** タスクバーが `FlashWindowEx` で点滅し、ペインをアクティブ化するか idle 通知が来るまで attention 表示が解除されない

### Requirement: TUI選択状態の確認ポップアップ
Level 1 の attention 表示(タイトル絵文字・タスクバー点滅)に加えて、amm は attention 状態のペイン(構造化された Level 2 の許可要求を伴わないもの、例えば Notification hook の `permission_prompt`/`elicitation_dialog` や OSC9 由来の attention 等)向けに、承認オーバーレイと同じ見た目・挙動の軽量な確認ポップアップを表示しなければならない (SHALL)。このポップアップは対象ペイン数を件数表示し、単一の「確認」ボタンのみを持つ。「確認」ボタンは対象ペインを最前面へ移動しアクティブ化するだけで、許可/拒否のような決定概念を持たない(Notification hook のペイロードには `tool_name`/`tool_input` が含まれないため、そもそも構造化された決定を下す材料が無い)。Level 2 の許可要求(承認オーバーレイ)が既に表示されているペインは、このポップアップの対象から除外しなければならない (SHALL NOT) — 承認オーバーレイ自身の「確認」導線と重複させないため。

#### Scenario: 構造化されていない attention 状態でポップアップが表示される
- **WHEN** 許可要求(Level 2)を伴わないペインが attention 状態になる
- **THEN** 確認ポップアップが表示され、対象ペインの件数とラベルを表示する

#### Scenario: 「確認」でペインへ移動し表示が消える
- **WHEN** 確認ポップアップの「確認」ボタンを押す
- **THEN** 対象ペインが最前面へ移動しアクティブ化され、そのペインの attention 表示が解除される
- **AND** attention 状態のペインが他に残っていなければポップアップは非表示になる

#### Scenario: 承認オーバーレイ対象のペインとは重複しない
- **WHEN** あるペインが Level 2 の許可要求(承認オーバーレイ)の対象になっている状態で、同じペインが attention 状態でもある
- **THEN** 確認ポップアップの対象からはそのペインを除外し、件数にも含めない

### Requirement: Level 2 — 許可要求の集約回答台帳
`ApprovalBroker` は CLI からの許可要求を `token` (ペイン識別子) / `toolName` / `toolInputJson` 付きの台帳エントリとして保持し、GUI からの回答 (`"allow"` / `"deny"`) または解放 (`null`) を待つ非同期 API (`RequestAsync`) を提供しなければならない (SHALL)。1 リクエスト = 1 エントリとして、複数ペイン・同一ペインの並列要求を独立に扱う。

#### Scenario: 回答による解決
- **WHEN** GUI が特定エントリを `Resolve(id, "allow")` で解決する
- **THEN** 対応する `RequestAsync` の Task が `"allow"` で完了し、エントリは台帳から除去される

#### Scenario: 二重解決は先勝ち
- **WHEN** 既に解決済みのエントリ ID に対し再度 `Resolve` を呼ぶ
- **THEN** 2 回目の呼び出しは `false` を返し、最初の解決結果のみが有効になる

### Requirement: 4 種の解放トリガー
台帳エントリは (1) 人間の回答、(2) 明示解放 (`Resolve(id, null)` / `ReleaseByToken` / `ReleaseAll`)、(3) 既定 45 秒のタイムアウト、(4) パイプ切断 (`CancellationToken`) のいずれかで必ず解放されなければならない (SHALL)。決定なし (`null`) で解放された要求は、hook がペイン内プロンプトへフォールバックする合図として扱われる。

#### Scenario: タイムアウトによる解放
- **WHEN** 45 秒 (既定) 経過しても人間が回答しない
- **THEN** エントリは `null` 決定で解放され台帳から除去される

#### Scenario: パイプ切断による解放
- **WHEN** hook プロセス消滅等でセッションの `CancellationToken` がキャンセルされる
- **THEN** 該当エントリは `null` 決定で解放され、幽霊要求としてポップアップに残らない

#### Scenario: ペイン単位の一括解放
- **WHEN** 特定ペイン (token) が(他のペインから)アクティブ化される、またはクローズされる
- **THEN** `ReleaseByToken` によりそのペイン由来の保留エントリのみが `null` 決定で解放され、他ペインの要求には影響しない

**2026-07-28 実機動作確認での修正**: 「アクティブ化」は非アクティブ状態からの遷移を指し、既にアクティブなペイン内での通常のクリック(ターミナルへのフォーカスクリック等)では解放してはならない (SHALL NOT)。実機テストで、許可要求が発生したペインで人間がそのまま作業を続けている(＝クリックし続ける)と、表示される間もなく解放され続けてしまう不具合が見つかったため修正した。承認オーバーレイの「確認」ボタン自体は、対象ペインが偶然既にアクティブだった場合でも明示的に解放を行う(ボタン押下という明確な意思表示のため、アクティブ化遷移の有無に関わらず解放する)。

#### Scenario: 既にアクティブなペイン内でのクリックでは解放しない
- **WHEN** あるペインが既にアクティブな状態で、そのペイン内でクリック等の操作を行う(ペインの切り替えを伴わない)
- **THEN** そのペイン由来の保留エントリは解放されない(アクティブ化の遷移が発生していないため)

### Requirement: 非モーダル集約ポップアップ UI
許可要求の集約 UI はフォーカスを奪わずに表示され、複数要求がある場合はウィンドウ（またはUI要素）を増やさず「1/N 件」表示で先頭から順に扱わなければならない (SHALL)。表示直後 500ms は誤操作防止のため「はい」/「確認」ボタンを無効化する。

**2026-07-27 UX見直し(ユーザー指示)**: ボタンを「はい」(即allow)と「確認」(要求元ペインへ移動、決定なしで解放)の2つのみに簡略化した。「拒否」(deny)と「閉じる」(✕)の専用ボタンは撤去し、拒否したい場合は「確認」でペインへ移動してCLI本体のネイティブな確認プロンプトで直接操作する導線に一本化している。ただし台帳API自体(`Resolve(id, "deny")`)と`amm-mcp.exe approve`のdeny出力契約(下記Requirement参照)は変更していない — GUIから明示的にdenyを送る手段が無くなっただけで、プロトコルレベルの機能は保持している。

.NET 版の `ApprovalPopupForm`（フォーカスを奪わない非アクティブ化ウィンドウ、`WS_EX_NOACTIVATE`）を Tauri へそのまま移植し、第2の `WebviewWindow` として実装したところ、2026-07-21 に実機デバッガ（cdb.exe）でアプリ全体を永久にデッドロックさせる不具合であることが判明した（Tauri の IPC がメイン webview 自身の CDP ネットワーク傍受経由でメイン UI スレッドに届くため、そのコールバック内側から第2の `CoreWebView2Controller` を同期生成しようとすると、その完了待ちがブラウザプロセス側の応答待ちと循環する）。このため、Tauri 版では第2のネイティブウィンドウを作らず、メインウィンドウ内の DOM オーバーレイ（固定位置 `div`、常に最前面レイヤーだがメインウィンドウの内部に限定）として実装しなければならない (SHALL)。この結果、.NET 版と異なり、amm のメインウィンドウが最小化中または他アプリの背後にある間はポップアップも見えなくなる（OS レベルでの常時最前面表示は提供しない）。この制約は、アプリ全体が使用不能になる設計より優先される許容トレードオフとする（経緯: UDR-amm-20260726T0745-194）。

#### Scenario: 複数要求のキュー表示
- **WHEN** 3 件の許可要求が同時に保留されている状態でオーバーレイが更新される
- **THEN** 先頭の 1 件のみが表示され「⚠ (1/3 件)」のラベルが付く

#### Scenario: 表示直後のクリックガード
- **WHEN** オーバーレイが新しい要求で表示されてから 500ms 以内にボタンをクリックしようとする
- **THEN** ボタンは無効化されておりクリックは効果を持たない

#### Scenario: メインウィンドウが最小化中は非表示
- **WHEN** amm のメインウィンドウが最小化されている、または他アプリの背後にある間に新しい承認要求が届く
- **THEN** オーバーレイはメインウィンドウの DOM 内に留まり、OS レベルでの最前面表示は行われない（メインウィンドウを前面化すれば見える）
- **AND** この間も CLI 側のインタラクティブな Yes/No/Cancel プロンプトによるフォールバック応答は引き続き機能する

#### Scenario: 「確認」ボタンで対象ペインへ切り替わり決定なしで解放する
- **WHEN** 保留中の許可要求が表示されている状態で「確認」ボタンを押す
- **THEN** 要求元のペインが最前面へ移動しアクティブ化される
- **AND** ペインのアクティブ化は既存の release トリガーの1つのため、この操作でも当該許可要求は決定なし (`null`) で解放される
- **AND** 台帳に残り続けてはならない (SHALL NOT) — 呼び出し元 CLI は自身のインタラクティブな確認プロンプトへフォールバックする

### Requirement: amm-mcp.exe approve サブコマンドの決定出力契約
`amm-mcp.exe approve` は環境変数 `AMM_NOTIFY_ID` が無い場合は no-op で終了し、決定 (allow/deny) を得た場合のみ `--source` に応じた CLI 別フォーマット (Claude Code: `hookSpecificOutput.decision.behavior`、Copilot CLI: `behavior` 直書き) の JSON を標準出力に書かなければならない (SHALL)。無回答時は何も出力せず終了コード 0 とする。

#### Scenario: Claude Code 向け allow 出力
- **WHEN** `--source claude` (または省略) で allow 決定を受け取る
- **THEN** `{"hookSpecificOutput":{"hookEventName":"PermissionRequest","decision":{"behavior":"allow"}}}` を標準出力に書く

#### Scenario: Copilot CLI 向け deny 出力
- **WHEN** `--source copilot` で deny 決定を受け取る
- **THEN** `{"behavior":"deny","message":"..."}` を標準出力に書く

#### Scenario: 無回答時は沈黙
- **WHEN** 45 秒の台帳タイムアウトにより決定なしで解放される
- **THEN** `amm-mcp.exe approve` は標準出力に何も書かず終了コード 0 で終了し、CLI 側は通常のペイン内プロンプトにフォールバックする
