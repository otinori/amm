## MODIFIED Requirements

### Requirement: 非モーダル集約ポップアップ UI
許可要求の集約 UI はフォーカスを奪わずに表示され、複数要求がある場合はウィンドウ（またはUI要素）を増やさず「1/N 件」表示で先頭から順に扱わなければならない (SHALL)。表示直後 500ms は誤操作防止のため許可/拒否ボタンを無効化する。

.NET 版の `ApprovalPopupForm`（フォーカスを奪わない非アクティブ化ウィンドウ、`WS_EX_NOACTIVATE`）を Tauri へそのまま移植し、第2の `WebviewWindow` として実装したところ、2026-07-21 に実機デバッガ（cdb.exe）でアプリ全体を永久にデッドロックさせる不具合であることが判明した（Tauri の IPC がメイン webview 自身の CDP ネットワーク傍受経由でメイン UI スレッドに届くため、そのコールバック内側から第2の `CoreWebView2Controller` を同期生成しようとすると、その完了待ちがブラウザプロセス側の応答待ちと循環する）。このため、Tauri 版では第2のネイティブウィンドウを作らず、メインウィンドウ内の DOM オーバーレイ（固定位置 `div`、常に最前面レイヤーだがメインウィンドウの内部に限定）として実装しなければならない (SHALL)。この結果、.NET 版と異なり、amm のメインウィンドウが最小化中または他アプリの背後にある間はポップアップも見えなくなる（OS レベルでの常時最前面表示は提供しない）。この制約は、アプリ全体が使用不能になる設計より優先される許容トレードオフとする。

#### Scenario: 複数要求のキュー表示
- **WHEN** 3 件の許可要求が同時に保留されている状態でオーバーレイが更新される
- **THEN** 先頭の 1 件のみが表示され「⚠ (1/3 件)」のラベルが付く

#### Scenario: 表示直後のクリックガード
- **WHEN** オーバーレイが新しい要求で表示されてから 500ms 以内にボタンをクリックしようとする
- **THEN** ボタンは無効化されておりクリックは効果を持たない

#### Scenario: メインウィンドウが最小化中は非表示
- **WHEN** amm のメインウィンドウが最小化されている、または他アプリの背後にある間に新しい承認要求が届く
- **THEN** オーバーレイはメインウィンドウの DOM 内に留まり、OS レベルでの最前面表示は行われない（メインウィンドウを前面化すれば見える）
- **AND** この間も CLI 側のインタラクティブな Yes/No/Cancel プロンプトによるフォールバック応答は引き続き機能する

#### Scenario: 「閉じる」ボタンは決定なしで解放する
- **WHEN** 保留中の許可要求が表示されている状態で「閉じる」(✕) ボタンを押す
- **THEN** 許可/拒否のいずれも選択されないまま台帳から解放される (decision なし、タイムアウト・ペインクローズ・ペインアクティブ化と同じ扱い)
- **AND** 台帳に残り続けてはならない (SHALL NOT) — 呼び出し元 CLI は自身のインタラクティブな確認プロンプトへフォールバックする

#### Scenario: 「ペインへ移動」ボタンで対象ペインへ切り替わる
- **WHEN** 保留中の許可要求が表示されている状態で「ペインへ移動」ボタンを押す
- **THEN** 要求元のペインが最前面へ移動しアクティブ化される
- **AND** ペインのアクティブ化は既存の release トリガーの1つのため、この操作でも当該許可要求は決定なしで解放される
