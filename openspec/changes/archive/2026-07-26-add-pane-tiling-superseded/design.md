## Context

`migrate-to-tauri` のTauri版 `app.js` は、ペインを `position:absolute` の自由配置で管理していた。タイトルバーの `mousedown` から始まるドラッグで任意座標へ移動でき、角の `.resize-handle` で個別に幅・高さを変更でき、「タイル」「カスケード」ボタンは押した瞬間だけ整列する一時的なコマンドだった(常時維持される制約ではない)。

ユーザーからの要望は、i3/sway・tmuxのような「常に隙間なく整列した状態を維持し、ドラッグで入れ替え・ドッキングでき、任意の1ペインを全画面表示⇔復帰できる」操作性への転換であり、既存の自由配置モデルとの共存(モード切替)ではなく完全な置き換えとして合意済み(会話内でユーザー承認済み)。

## Goals / Non-Goals

**Goals:**
- 常時タイリング状態(隙間なし)を維持する可変分割ツリー(BSP)によるペインレイアウト
- ドラッグ&ドロップによる、ペイン同士の入れ替え・任意位置への再ドッキング(VS Codeのエディタグループ分割に類似した5分割ドロップゾーンUI)
- 分割の境界線(ディバイダー)をドラッグしたリサイズ
- 任意の1ペインの全画面表示(ズーム)トグルと、元の分割ツリー形状を保った復帰
- レイアウト(分割ツリーの形・比率・どのペインがどの葉か)の再起動後永続化

**Non-Goals:**
- プロファイル単位の記憶済みジオメトリ(`x/y/w/h`)を分割比率へ自動変換する対応(将来の改善として持ち越し。今回は「アクティブペインを分割してドッキング」に一本化し、記憶済み `x/y/w/h` は新規ペイン挿入位置には使わない)
- タイリングと自由配置の共存(トグルモード)。今回は完全置き換えのみ
- Rust側(`src-tauri`)の変更。既存の `pty_resize`/`capture_window_geometry`/`resolve_geometry_apply_plan` はいずれもレイアウトモデルに非依存な契約のままで足りる

## Decisions

### 分割ツリー(BSP)をペインレイアウトのデータモデルに採用
`app.js` にモジュールレベルの木構造 `tilingRoot` を新設する。Leaf `{type:'leaf', pane}` / Split `{type:'split', dir:'row'|'col', ratio, a, b, dividerEl}`。`row` = 左右分割(縦の仕切り線)、`col` = 上下分割(横の仕切り線)。

代替案として「固定グリッド+スワップ」(グリッドの升目に対してペインをスワップするだけの単純な方式)も検討したが、ユーザーが明示的にBSP方式(i3/sway/tmux相当、任意の入れ子・任意比率の分割が可能)を選択した。

### 新規ペインは常にアクティブペインの右側分割で挿入
tmuxの `%`(垂直分割で右に新ペイン)に相当する挙動をデフォルトとする。ドラッグ&ドロップでの端ドロップ挿入は同じ `insertPaneIntoTree` 関数を、`dir` を上下左右いずれでも渡せる形で共用する。

### ドラッグ操作の意味の転換(自由移動 → ドッキング)
タイトルバーの `mousedown` ドラッグ中、カーソル下のペインの矩形を上下左右中央5分割し、該当ゾーンをオーバーレイでハイライトする(VS Codeのエディタグループ分割と同様のUI)。`mouseup` 時、中央ドロップなら2ペインの位置を入れ替え(`swapPanesInTree`)、端ドロップなら元の位置から取り除いて対象の指定方向へ再挿入する(`removePaneFromTree` → `insertPaneIntoTree`)。オーバーレイの実装は既存の `showCtxMenu`(append→次フレームで測定→クランプの2段階パターン)を踏襲する。

### リサイズハンドル(角)→ ディバイダードラッグへの置き換え
個別ペインの角をドラッグしてサイズを変える方式は、隣接ペイン間に隙間や重なりを生み常時タイリングの制約と両立しないため廃止した。分割ノードごとに生成する `.tile-divider` 要素をドラッグして、その分割の比率(`ratio`)のみを変更する方式に統一する。ドラッグ中は毎 `mousemove` で両側のペインに対し `fitAddon.fit()` + `invoke('pty_resize', ...)` を呼ぶ(既存の `.resize-handle` ドラッグ時と同じ「継続的にfit+resizeし、`mouseup` で1回だけ `saveLayout()`」というパターンをそのまま踏襲)。

### ズーム(全画面表示トグル)はツリー形状を変更しない
`zoomedPane` を別途保持し、セットされている間は他ペイン・ディバイダーを非表示にしてズーム対象のみをデスク全域に表示する。ツリー自体は一切変更しないため、解除時に元の分割・比率へ寸分違わず戻る。トリガーはタイトルバー専用の「⛶」アイコン(ダブルクリックはドラッグ開始の `mousedown` ハンドラと衝突するため使わない)。

### 永続化は分割ツリーをそのままシリアライズ
`serializeTree`/`deserializeTree` を新設し、`{type:'leaf', displayId}` / `{type:'split', dir, ratio, a, b}` の形で `localStorage` に保存する。起動時は「保存済みツリーの葉が要求するペインを先にすべて作成 → `displayId` で紐付けてツリーを再構築 → 一致しなければ均等分割ツリーへフォールバック」という2段階シーケンスに変更する(旧実装は保存済み矩形ごとに `createPane` を呼ぶだけの1段階だった)。

## Risks / Trade-offs

- [Risk] プロファイル単位の記憶済みジオメトリ(`x/y/w/h`)が新規ペイン挿入位置に反映されなくなり、`capture_window_geometry`/`resolve_geometry_apply_plan` の一部フィールドが実質的に読み捨てられる → [Mitigation] `maximized`/`name`/`workingDirectory` は引き続き有効。`x/y/w/h` をタイリング挿入位置へ変換する対応は明示的にNon-Goalsとして持ち越し、UIの「配置を記憶」操作自体は引き続き動作する(捕捉した値は将来の改善まで温存される)
- [Risk] ドラッグ&ドロップのドロップゾーン判定(中央/上下左右)がユーザーの意図と食い違う誤操作を招く可能性 → [Mitigation] VS Codeのエディタグループ分割で広く実績のある5分割(中央40%を「入れ替え」、残りを4方向の「ドッキング」に按分)のUIパターンを踏襲し、実機検証で誤操作しやすい境界がないか確認する
- [Risk] 実機(Windows、Tauri WebView2)でのみ検証可能な変更であり、Linuxコンテナ上のCI/この開発環境では動作確認できない → [Mitigation] 静的レビュー(構文チェック・関数間の参照整合性)で作業時点の破損を防ぎつつ、`tests/e2e-tauri` のCDP経由手法で実機検証を別タスクとして明示的に残す

## Migration Plan

- Rust側の変更は不要なため、`cargo build`/`cargo test` は既存分の回帰確認のみで足りる
- `app.js`/`style.css`/`index.html` の変更はビルド不要(静的ファイル配信)。実機での動作確認(下記)を経てから `main` への統合PRを作成する
- ロールバック: 本変更は新規 change のブランチ上で完結するため、問題があれば単純にPRをマージしないことでロールバック可能。`localStorage` の保存形式が変わるため、旧形式の保存データは新形式のパースに失敗し空扱いになる(既定の均等分割ツリーへフォールバックするため、起動不能にはならない)
